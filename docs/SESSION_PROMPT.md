# Session prompt

Paste the block below at the start of a new development session. Update "Open work" when it goes
stale; the rest should rarely change.

---

```text
Before writing any code, get your bearings on chess-trainer. Do not change anything yet.

1. Read docs/PROJECT_BRIEF.md and CLAUDE.md. The brief is the spec. If it contradicts the code or
   this prompt, or if a request is ambiguous, ask me instead of inventing.

2. Check the real state, and do not trust memory or this prompt over it:
   - git status, the current branch, and git log origin/main -5
   - open pull requests and their CI: gh pr list
   - whether the app runs: docker compose ps, then GET http://127.0.0.1:8000/api/health

3. Tell me in a few lines: what state the repo is in, anything unexpected, and your plan for what I
   asked. If the work is more than a small fix, wait for my approval before starting.

Language: talk to me in Brazilian Portuguese. Code, comments, commits and docs are in English.

How we work:
- Discuss first when I am thinking aloud. A question like "what do you think?" is not a request to
  implement. If you are unsure which it is, ask.
- Commit, push, open a PR or merge only when I ask. Keep my .vscode/ and other untracked local files
  out of commits: add files by path, never everything.
- Small commits, on a new branch from an up-to-date main. Before pushing, run lint and tests on a
  clean checkout of the commit, because passing locally can hide files that were never committed.
- If a PR is stacked on another, its base does not move to main by itself. Prefer one PR at a time
  against main. After any merge, check that the commits really are on origin/main.
- Do not poll CI. Auto-merge is not allowed in this repository.
- Be careful with cost: this conversation's size is what costs the most. Do not read what you do not
  need, and suggest a new session when a task is finished rather than continuing a long one.
- Report honestly: what was tested, what was not, and any mistake of yours. You cannot hear sounds,
  and passing tests do not prove something looks right, so look at a screenshot for visual work.

Testing:
- Lint: uv run ruff check . && uv run ruff format --check .
- Unit and API: uv run pytest
- Book: uv run python -m catalog.validate
- Engine: scripts/extract-stockfish.sh, then STOCKFISH_PATH=.cache/stockfish uv run pytest -m engine
- Image: scripts/smoke.sh chess-trainer:local
- Browser: while the project is in development the app's data is disposable, so rebuild and
  restart the app on port 8000 and test against it, with no separate container:
    docker compose up -d --build
    E2E_BASE_URL=http://127.0.0.1:8000 uv run pytest -m e2e
  Tests run at 1280x720, the smallest supported screen. Mobile is out of scope.
- The app's web files are inside the image: after changing them, rebuild, and reload the browser
  with Ctrl+Shift+R.

Rules that are easy to break:
- Never change or reuse a line id in openings/, even when extending its moves.
- The database is local, in ./data. Schema changes are new numbered migrations. Never delete data
  without a migration and a note.
- No theory moves from memory: lines come from the catalog or a source recorded in `source`.
- Only PGN goes in and out. Never accept a loose FEN; a [FEN] tag is accepted only for Chess960, and
  the Chess960 setup takes a typed FEN of one of its 960 starting positions.
- No statistics: this is a training tool.
- Nothing loads from a CDN, and third-party assets must be compatible with GPL-3.0 and listed in
  THIRD_PARTY_LICENSES.md.
- Keep personal details about me, such as my rating or repertoire, out of the repository.

Open work, as of 2026-11-10 (verify before relying on it):
- Starting a new game from a saved Chess960 game. Chess960 itself can be played, and reviewed.
- Calibrating the bot levels, which have not been measured.
- Reviewing the pt-BR and es opening names by a chess player. They were generated by rules, and
  catalog.validate reports the coverage.
- Replacing the generated sounds with recorded ones, which I will provide.
```
